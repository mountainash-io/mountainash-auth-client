# Frequently Asked Questions for Mountainash Auth Client

## Auth Type System

### What are the 13 auth types supported by mountainash-auth-client?

The library supports a discriminated union of 13 authentication types, each represented as a frozen Pydantic model with a Literal `kind` discriminator field. The types are: **NoAuth** (for unauthenticated endpoints), **PasswordAuth** (username/password credentials), **TokenAuth** (static bearer or API tokens), **JWTAuth** (JSON Web Tokens), **OAuth2Auth** (OAuth 2.0 client credentials or pre-obtained tokens), **OAuth2AuthCodeAuth** (OAuth 2.0 Authorization Code with PKCE), **OAuth1Auth** (OAuth 1.0a three-legged flow), **IAMAuth** (cloud IAM role-based authentication), **AzureADAuth** (Azure Active Directory), **WindowsAuth** (Windows Integrated/NTLM), **KerberosAuth** (Kerberos ticket-based), **CertificateAuth** (mutual TLS with client certificates), and **ServiceAccountAuth** (service account key files). Each type carries only the fields relevant to its authentication method, and the frozen model constraint ensures credentials are immutable after construction. The discriminated union design means the type system itself prevents invalid combinations of auth fields.

### What is a discriminated union and why does the library use one?

A discriminated union is a type pattern where multiple distinct types share a common discriminator field that uniquely identifies which variant is in use. In mountainash-auth-client, each auth type model has a `kind` field set to a Literal string value (e.g., `kind: Literal["oauth2"]`). This allows Pydantic to inspect the `kind` value at parse time and select the correct model variant, providing full runtime validation and static type checking. The benefit is that code receiving an auth specification can pattern-match on the `kind` field to handle each variant with complete type safety. Compared to a single model with many optional fields, the discriminated union guarantees that you never have an OAuth2 config missing its `client_id` or a PasswordAuth accidentally carrying a `refresh_token`. Each variant is self-contained, minimal, and validated independently. This approach also integrates cleanly with the dispatch registry, which maps each `kind` string to the appropriate driver kwargs function.

### What is the AuthSpec base model and how do all auth types inherit from it?

AuthSpec is the base Pydantic model from which all 13 auth type variants derive. It is configured as a frozen model, meaning instances are immutable after creation. AuthSpec defines the shared contract that every auth variant must satisfy, primarily the `kind` discriminator field. Each concrete auth type inherits from AuthSpec and adds its own specific fields. For example, OAuth2AuthCodeAuth adds `client_id`, `client_secret`, `authorize_url`, `token_url`, and PKCE-related fields, while PasswordAuth simply adds `username` and `password`. The frozen constraint inherited from AuthSpec ensures that once an auth configuration is constructed, its credentials cannot be accidentally mutated. This immutability is important for thread safety and for preventing credential leakage through unintended modification. The discriminated union itself is defined as a type alias that is the Union of all 13 concrete types, with `kind` as the discriminator.

### What is the Literal kind discriminator and how does it enable type-safe dispatch?

The Literal kind discriminator is a Pydantic field on each auth type model set to a specific string constant using Python's `Literal` type. For instance, OAuth2Auth might declare `kind: Literal["oauth2"] = "oauth2"`, while TokenAuth declares `kind: Literal["token"] = "token"`. When Pydantic encounters a dictionary or JSON payload, it reads the `kind` field first and uses it to select which model variant to parse against. This mechanism enables type-safe dispatch at two levels. First, Pydantic validates that only the fields belonging to the matched variant are present. Second, downstream code can use the `kind` value to look up the correct handler in the auth dispatch registry, confident that the model has already been validated for that variant. Static type checkers like mypy or pyright can narrow the type based on `kind` checks, giving full autocompletion and type safety in each branch.

### When should I use OAuth2Auth versus OAuth2AuthCodeAuth?

Use **OAuth2Auth** when you already have a valid access token or when the API provider uses the client credentials grant (machine-to-machine). OAuth2Auth carries the token directly and does not manage an interactive authorization flow. Use **OAuth2AuthCodeAuth** when the API requires user consent through a browser-based authorization flow. OAuth2AuthCodeAuth includes the full Authorization Code with PKCE flow: it stores `authorize_url`, `token_url`, `client_id`, scopes, and PKCE parameters, and integrates with the connection mixin to handle token exchange, refresh, and expiry automatically. If the API you are integrating with requires the user to sign in via a browser and grant permissions (such as Google, GitHub, or Microsoft APIs), OAuth2AuthCodeAuth is the correct choice. If you are working with service-to-service APIs where no user interaction is required, or you have a long-lived token from another source, OAuth2Auth is simpler and sufficient.

### What are the NoAuth and PasswordAuth types used for?

**NoAuth** is the simplest auth type variant, representing endpoints that require no authentication at all. It exists in the discriminated union so that connection configurations can be fully typed even when no credentials are needed. Without NoAuth, unauthenticated connections would need special-case handling or None values, breaking the uniform dispatch pattern. **PasswordAuth** carries a username and password pair for APIs that use HTTP Basic authentication or similar credential-based schemes. It is frozen like all auth types, so the password cannot be mutated after construction. PasswordAuth is suitable for legacy APIs, internal services, or systems that use username/password pairs directly rather than tokens. Both types participate in the dispatch registry like any other auth variant, ensuring that driver kwargs generation remains consistent regardless of the authentication method in use.

### What are the IAMAuth, AzureADAuth, WindowsAuth, KerberosAuth, CertificateAuth, and ServiceAccountAuth types?

These six auth types handle enterprise and cloud-specific authentication scenarios. **IAMAuth** represents cloud IAM role-based authentication (such as AWS IAM roles) where credentials are derived from the execution environment. **AzureADAuth** handles Azure Active Directory authentication with tenant and client identifiers. **WindowsAuth** supports Windows Integrated Authentication (NTLM) for on-premises Microsoft services. **KerberosAuth** provides Kerberos ticket-based authentication for enterprise environments with KDC infrastructure. **CertificateAuth** supports mutual TLS authentication using client certificate and key files. **ServiceAccountAuth** handles service account key files typically used by cloud providers like Google Cloud. These types are classified as "unmapped" in the dispatch registry by default because their driver handling varies significantly across backends. Implementations consuming these types provide backend-specific handling rather than using the generic dispatch path.

## OAuth 2.0 and PKCE

### How does the OAuth 2.0 Authorization Code flow with PKCE work in this library?

The library implements the OAuth 2.0 Authorization Code flow with PKCE (Proof Key for Code Exchange) through the OAuthFlow class. The flow proceeds in several steps. First, a cryptographically random code verifier is generated. A code challenge is derived from the verifier using SHA-256 hashing and base64url encoding. The library then builds an authorization URL that includes the code challenge, a random state parameter for CSRF protection, the requested scopes, and the redirect URI. The user is directed to this URL in a browser. After the user grants consent, the provider redirects back with an authorization code and the state parameter. The LocalCallbackServer captures this redirect. The library then exchanges the authorization code for tokens by sending the code along with the original code verifier to the token endpoint. The provider verifies the code verifier against the stored challenge, preventing authorization code interception attacks. The resulting access token, refresh token, and expiry timestamp are stored via the SecretStore.

### What is PKCE and why is it important for security?

PKCE (Proof Key for Code Exchange, pronounced "pixy") is an extension to the OAuth 2.0 Authorization Code grant defined in RFC 7636. It prevents authorization code interception attacks where a malicious application on the same device intercepts the authorization code from the redirect URI and exchanges it for tokens. Without PKCE, any application that can observe the redirect can steal the authorization code. With PKCE, the legitimate client generates a random code verifier and sends a derived code challenge with the authorization request. When exchanging the code for tokens, the client must present the original code verifier. Since the attacker never had the code verifier, they cannot complete the exchange even if they intercept the authorization code. The library generates the code verifier as a cryptographically random string, computes the SHA-256 code challenge, and includes both in the appropriate protocol messages. PKCE is mandatory for public clients (like CLI tools) and strongly recommended for all clients.

### What is the state parameter and how does it protect against CSRF?

The state parameter is a cryptographically random string included in the OAuth authorization request and returned unchanged in the redirect callback. It serves as a CSRF (Cross-Site Request Forgery) protection mechanism. When the library builds the authorization URL, it generates a unique state value and includes it as a query parameter. When the OAuth provider redirects the user back after authorization, it includes this same state value. The LocalCallbackServer or manual redirect handler verifies that the returned state matches the original. If an attacker crafted a malicious authorization redirect (perhaps using their own authorization code), the state parameter would not match, and the library would reject the exchange. This prevents attackers from tricking users into linking their accounts to the attacker's identity provider account. The state parameter works alongside PKCE to provide defense in depth for the authorization flow.

### How does token refresh work and what happens when a refresh fails?

When the OAuth2ConnectionMixin detects that an access token has expired (via the token expiry check), it attempts an automatic refresh using the stored refresh token. The refresh is performed under a file lock to prevent concurrent processes from racing to refresh the same token simultaneously. The mixin sends the refresh token to the token endpoint and receives a new access token, a new expiry timestamp, and optionally a new refresh token. The updated credentials are saved to the SecretStore atomically. If the refresh fails, the library raises a **TokenRefreshError** that includes the HTTP status code from the provider's response. Common failure reasons include: the refresh token has been revoked, the refresh token has expired (some providers expire them), or the provider's token endpoint is unreachable. When a refresh fails and no valid token exists, the token lifecycle transitions to the "expired-no-refresh" state, and subsequent connection attempts raise **AuthorizationRequired**, prompting the user to re-authorize through the browser flow.

### What is the OAuthFlow class and what role does it play?

The OAuthFlow class encapsulates the complete OAuth 2.0 authorization and token management logic. It is a Pydantic model that holds the OAuth provider configuration: authorize URL, token URL, client ID, client secret, scopes, and redirect URI. Its primary methods include `build_authorize_url` (which generates the authorization URL with PKCE challenge and state parameter), `exchange_code` (which trades an authorization code and code verifier for tokens), and `refresh_token` (which obtains a fresh access token using a refresh token). The OAuthFlow also provides `end_to_end_authorize`, a convenience method that orchestrates the full flow: building the URL, launching the callback server, waiting for the redirect, and exchanging the code. OAuthFlow is used internally by OAuth2ConnectionMixin but can also be used standalone when custom flow control is needed. It is designed as a stateless utility: it does not store tokens itself but returns them for the caller (typically the connection mixin and SecretStore) to persist.

### How does OAuth 1.0a differ from OAuth 2.0 in this library?

OAuth 1.0a is supported through the OAuth1Flow class and OAuth1ConnectionMixin, which implement the three-legged OAuth 1.0a flow. Unlike OAuth 2.0's Authorization Code + PKCE flow, OAuth 1.0a uses a request token / verifier exchange pattern without PKCE. The three legs are: (1) obtain a request token from the provider, (2) redirect the user to authorize the request token, and (3) exchange the authorized request token and verifier for an access token. OAuth 1.0a requires cryptographic request signing for every API call, which the library delegates to the **authlib** library. Because authlib is an optional dependency, OAuth 1.0a support uses an import guard: if authlib is not installed, attempting to use OAuth1Auth raises a clear error explaining the missing dependency. OAuth 1.0a tokens typically do not expire, so the token lifecycle is simpler than OAuth 2.0. The OAuth1ConnectionMixin provides the same `connect` method interface as OAuth2ConnectionMixin, maintaining a consistent API.

### What is the LocalCallbackServer and when is it used?

The LocalCallbackServer is an ephemeral HTTP server that listens on localhost to capture OAuth redirect callbacks. During the Authorization Code flow, after the user grants consent in their browser, the OAuth provider redirects the browser to a redirect URI (typically `http://localhost:<port>/callback`). The LocalCallbackServer starts, waits for this single redirect request, extracts the authorization code and state parameter from the query string, and then shuts down. It runs as a context manager so the server is cleaned up automatically. The server is used by the `end_to_end_authorize` method of OAuthFlow. For environments where a local server is not feasible (headless servers, SSH sessions, containers), the library offers a **manual redirect mode** via `prompt_for_code`, where the user is shown the authorization URL and asked to paste the code or redirect URL back into the terminal. This fallback ensures the library works across all environments.

## Token Lifecycle and Connection Mixins

### What are the five states in the token lifecycle state machine?

The token lifecycle is a five-state machine that tracks the current status of OAuth credentials within a connection mixin. The states are: (1) **No Token** -- no credentials exist yet; the user has never authorized. The mixin must initiate the full authorization flow. (2) **Valid Token** -- a non-expired access token is available and ready to use for API calls. (3) **Expired With Refresh** -- the access token has expired but a valid refresh token is available. The mixin will attempt an automatic, file-locked refresh. (4) **Expired No Refresh** -- the access token has expired and no refresh token is available (or the refresh token itself has expired/been revoked). Re-authorization through the browser flow is required. (5) **Cleared** -- the credentials have been explicitly cleared via the SecretStore's clear method, leaving a tombstone marker. This is distinct from "no token" because it represents an intentional revocation. The mixin checks token expiry on each `connect` call and transitions between states automatically.

### What is OAuth2ConnectionMixin and how do I use it?

OAuth2ConnectionMixin is a mixin class that adds automatic OAuth 2.0 token lifecycle management to connection classes. You mix it into your connection class alongside your base connection class, and it provides the `connect` method that handles the full token lifecycle: checking for existing tokens, validating expiry, refreshing if needed, and initiating authorization if no valid token exists. Key features include the `auto_authorize` flag (which controls whether the mixin automatically opens the browser for new authorizations or raises AuthorizationRequired), the `profile` parameter (which allows multiple user profiles to maintain separate credentials), and context manager support for clean connection teardown. The `client` property provides the authenticated HTTP client after connecting. To use it, you configure an OAuth2AuthCodeAuth instance with provider details, pass it to your connection class, and call `connect()`. The mixin handles everything from PKCE flow initiation through token storage and refresh.

### What is the auto_authorize flag and when should I disable it?

The `auto_authorize` flag on OAuth2ConnectionMixin controls whether the mixin automatically initiates the browser-based authorization flow when no valid token exists. When set to `True` (the default), calling `connect()` without existing credentials will open the user's browser to the authorization URL and start the LocalCallbackServer to capture the redirect. When set to `False`, the same scenario raises an `AuthorizationRequired` error instead. You should disable auto_authorize in several scenarios: automated pipelines and CI/CD environments where no browser is available; background services where interactive authorization is inappropriate; applications that want to handle the authorization flow in a custom UI; and testing scenarios where you want to verify that credentials exist without triggering side effects. Disabling auto_authorize lets the calling application decide when and how to present the authorization flow to the user, rather than having the mixin take over.

### How does file-locked refresh prevent race conditions?

When multiple processes or threads share the same credential store (for example, parallel API workers using the same OAuth tokens), there is a risk that multiple processes detect an expired token simultaneously and all attempt to refresh it. This can cause problems: some providers invalidate the old refresh token upon issuing a new one, so the second process's refresh attempt would fail because it is using a now-invalidated refresh token. The library prevents this through file-locked refresh. When a connection mixin detects an expired token and begins the refresh flow, it first acquires a file lock via the SecretStore's `lock` method. Only one process can hold this lock at a time. The lock holder refreshes the token and saves the new credentials. Other processes waiting on the lock will acquire it, re-read the credentials from the store, find a valid token, and skip the refresh entirely. This ensures exactly one refresh occurs per expiry cycle, regardless of how many concurrent processes are running.

### What is the profile parameter and how does it support multi-user scenarios?

The `profile` parameter on connection mixins allows multiple user identities to maintain separate credential sets for the same API provider. When you call `connect(profile="alice")`, the mixin stores and retrieves Alice's tokens separately from the default profile or any other named profile. The profile name flows through to the SecretStore, which uses it as part of the namespace for credential storage. In FilesystemStore, profiles result in separate YAML files within the domain/provider directory. This is useful in applications that manage connections on behalf of multiple users (such as a server that acts as an agent for different team members), CLI tools that support multiple accounts, and testing scenarios where you need isolated credential sets. The `list_users` method on SecretStore returns all profiles that have stored credentials for a given provider.

### How does context manager support work with connection mixins?

Connection mixins implement Python's context manager protocol (`__enter__` and `__exit__`), allowing them to be used with `with` statements or `async with` for clean resource management. When entering the context, the mixin calls `connect()` to establish the authenticated session, including any necessary token refresh or authorization. When exiting the context, the mixin performs cleanup such as closing HTTP client sessions and releasing file locks. Using the context manager pattern ensures that resources are released even if an exception occurs during API calls. The pattern looks like `with MyConnection(auth=auth_spec) as conn: conn.client.get(...)`. Without the context manager, you would need to manually call `connect()` and handle cleanup in a `try/finally` block. The context manager support builds on Python's standard `contextlib` patterns and integrates with the connection mixin's lifecycle management.

## Secret Storage

### What is the SecretStore protocol and what methods must implementations provide?

SecretStore is a Python Protocol (structural subtyping interface) that defines the contract for credential storage backends. Any class that implements the required methods is a valid SecretStore without needing to inherit from a base class. The required methods are: **load(domain, provider, profile)** -- retrieves stored credentials, returning None if none exist; **save(domain, provider, profile, data)** -- persists credentials; **clear(domain, provider, profile)** -- marks credentials as cleared (using tombstone semantics rather than deletion); **is_cleared(domain, provider, profile)** -- checks whether credentials were explicitly cleared; **list_users(domain, provider)** -- returns all profiles with stored credentials; and **lock(domain, provider, profile)** -- returns a context manager for exclusive access during token refresh. The protocol design means you can implement custom backends for HashiCorp Vault, AWS Secrets Manager, OS keyrings, database storage, or any other credential system without modifying the library itself.

### How does FilesystemStore work and what security measures does it use?

FilesystemStore is the built-in SecretStore implementation that persists credentials as YAML files on the local filesystem. It organizes credentials in a directory hierarchy based on domain and provider namespace, with separate files for each user profile. Security measures include: **file permissions** set to owner-only read/write (mode 0600) so other users on the system cannot read credential files; **atomic file writes** that write to a temporary file and rename it into place, preventing partial writes from corrupting credentials if the process crashes mid-save; **file locking** via the lock method for concurrent-safe token refresh across multiple processes; and **tombstone semantics** for the clear operation, which writes a tombstone marker rather than deleting the file, allowing the system to distinguish between "never authorized" and "explicitly revoked." YAML serialization is used for human-readability during debugging while remaining machine-parseable.

### What are tombstone semantics and why does the library use them?

Tombstone semantics means that when credentials are cleared (revoked or logged out), the library writes a special marker (tombstone) to the credential file rather than deleting it. This design creates a meaningful distinction between two states that would otherwise be indistinguishable: "no token has ever been stored" (the No Token state) and "a token existed but was explicitly cleared" (the Cleared state). This distinction matters for user experience and security. When a user has never authorized, the application should prompt them to authorize. When a user has explicitly revoked their credentials, the application should inform them that their session was cleared and ask if they want to re-authorize, rather than silently starting a new authorization flow. Tombstones also provide an audit trail showing that credentials were intentionally revoked. The `is_cleared` method on SecretStore checks for the presence of a tombstone, enabling the connection mixin to handle each case appropriately.

### How does the domain/provider namespace work in FilesystemStore?

FilesystemStore organizes credential files using a two-level namespace: domain and provider. The domain typically represents the API service being accessed (such as "github" or "google"), while the provider identifies the specific OAuth configuration or deployment. Together, they form a directory path within the store's base directory. For example, credentials for a GitHub OAuth app might be stored at `<base_dir>/github/oauth-app/<profile>.yaml`. This namespacing prevents credential collisions when the same application connects to multiple API providers or when multiple applications share the same credential store directory. The `list_users` method scopes its results to a specific domain/provider pair, returning only the profiles relevant to that provider. This organizational scheme scales well as the number of integrated services grows and keeps credentials for different providers isolated from each other.

### How can I implement a custom SecretStore backend?

To implement a custom SecretStore backend, create a class that satisfies the SecretStore protocol by implementing all six required methods: `load`, `save`, `clear`, `is_cleared`, `list_users`, and `lock`. Because SecretStore is a Protocol, you do not need to inherit from any base class; structural subtyping means any class with the correct method signatures is automatically compatible. For example, to build a Vault-backed store, your `load` method would read from HashiCorp Vault's KV secrets engine, `save` would write to it, and `lock` would use Vault's session-based locking or a separate distributed lock. For an OS keyring backend, you might use the `keyring` Python package for `load` and `save`, with `lock` using a platform-specific mutex. Key considerations: ensure `clear` implements tombstone semantics (mark as cleared rather than delete), ensure `lock` returns a context manager for exclusive access, and handle the case where `load` returns None for never-stored credentials. The connection mixins will work with any conforming implementation without modification.

## Auth Dispatch

### What is the auth dispatch registry and how does it work?

The auth dispatch registry is a mapping from auth type `kind` strings to functions that convert an auth spec into driver-specific keyword arguments. When a backend (such as a REST client or database connector) needs to authenticate a request, it passes the auth spec to the dispatch registry, which looks up the `kind` value, finds the corresponding function, and calls it to produce the kwargs the driver needs. For example, the registry might map `"token"` to a function that extracts the token and returns `{"headers": {"Authorization": f"Bearer {token}"}}`, while `"password"` maps to a function returning `{"auth": (username, password)}`. This indirection decouples auth type definitions from backend-specific implementation details. Each backend can register its own set of dispatch functions, and the registry pattern means adding a new auth type only requires adding a new entry rather than modifying existing code. The `auth_to_driver_kwargs` function is the main entry point for this conversion.

### What are unmapped auth types and how does backend-specific handling work?

Unmapped auth types are the six enterprise/cloud auth variants (IAMAuth, AzureADAuth, WindowsAuth, KerberosAuth, CertificateAuth, ServiceAccountAuth) that do not have entries in the default dispatch registry. These types are "unmapped" because their authentication mechanisms vary so significantly across backends that a generic dispatch function is not feasible. For example, IAMAuth on AWS requires SigV4 request signing, while the same concept on GCP uses a completely different credential chain. When the dispatch registry encounters an unmapped auth type, it falls through to backend-specific handling. Each backend implementation is responsible for providing its own handling of these types, typically through conditional logic that checks the `kind` field and applies the appropriate authentication mechanism. This design keeps the core dispatch registry simple and generic while allowing backends to implement sophisticated, provider-specific authentication without polluting the shared codebase.

### How do I add a new auth type to the dispatch system?

Adding a new auth type involves three steps. First, create a new frozen Pydantic model that inherits from AuthSpec and defines a unique `kind` Literal value and the fields required for the authentication method. For example, `class CustomHeaderAuth(AuthSpec): kind: Literal["custom_header"] = "custom_header"; header_name: str; header_value: str`. Second, add the new model to the discriminated union type alias so Pydantic can parse it. Third, register a dispatch function in the auth dispatch registry that converts the new auth type into driver kwargs. The dispatch function receives the auth spec instance and returns a dictionary of keyword arguments suitable for the target driver. For example: `{"headers": {spec.header_name: spec.header_value}}`. If the new auth type requires backend-specific handling (like the enterprise types), you can leave it unmapped in the default registry and implement handling in each backend individually. The frozen model constraint and Literal discriminator ensure the new type integrates safely with existing validation and dispatch infrastructure.

## Error Handling and Troubleshooting

### What errors can occur during token exchange and how should I handle them?

**TokenExchangeError** is raised when the library fails to exchange an authorization code for access tokens at the OAuth provider's token endpoint. The error includes the token exchange URL so you can identify which provider failed. Common causes include: an expired authorization code (codes typically expire within minutes), a mismatched redirect URI between the authorization request and the token exchange, an incorrect client secret, PKCE code verifier mismatch, or the provider's token endpoint being unreachable. To handle this error, catch `TokenExchangeError`, log the failure details (including the URL), and prompt the user to retry the authorization flow. Do not retry the token exchange itself because the authorization code is single-use and likely expired. Instead, restart the full authorization flow from the beginning, which will generate fresh PKCE parameters and a new authorization code.

### What is TokenRefreshError and when does it occur?

**TokenRefreshError** is raised when the library fails to refresh an expired access token using the stored refresh token. The error includes the HTTP status code returned by the provider's token endpoint, which helps diagnose the cause. Common status codes include: 400 (invalid request, often meaning the refresh token is malformed or expired), 401 (invalid client credentials), and 403 (refresh token has been revoked). Refresh tokens can be invalidated for several reasons: the user revoked access in the provider's settings, the provider rotated the refresh token and the old one was used, the provider's refresh token expiry policy triggered, or an administrator revoked all tokens for the application. When TokenRefreshError occurs, the token lifecycle transitions to the "expired-no-refresh" state. The next connection attempt will either initiate a new authorization flow (if auto_authorize is True) or raise AuthorizationRequired (if auto_authorize is False). Applications should catch this error and inform users that re-authorization is needed.

### What is AuthorizationRequired and when is it raised?

**AuthorizationRequired** is raised when a connection mixin needs valid credentials but cannot obtain them automatically. This occurs in three scenarios: (1) no token exists and `auto_authorize` is False, meaning the mixin will not initiate the browser flow on its own; (2) the token has expired with no refresh token available and auto_authorize is False; (3) credentials have been explicitly cleared (tombstone state) and auto_authorize is False. The error includes provider and user context information so the calling application can construct a meaningful message for the user. The intended handling pattern is to catch AuthorizationRequired at the application level, present the user with an option to authorize (perhaps through a custom UI), and then either call `connect(auto_authorize=True)` or invoke the OAuthFlow directly. This error is the library's way of saying "I need human intervention" without taking action that might be inappropriate for the application's context (such as opening a browser on a headless server).

### How do I troubleshoot "Token refresh failed with status 401"?

A 401 status on token refresh typically means the client credentials (client ID and/or client secret) are invalid at the provider's token endpoint. Steps to diagnose: First, verify that the client ID and client secret in your OAuth2AuthCodeAuth configuration match what the provider has on file. Client secrets can be rotated or regenerated in the provider's developer console, invalidating the previous value. Second, check whether the provider requires the client credentials as a Basic auth header versus a POST body parameter; some providers are strict about this. Third, confirm the token endpoint URL is correct and has not changed. Fourth, check if the provider has revoked or disabled your OAuth application. If the client credentials are correct, the refresh token itself may have been invalidated server-side. In that case, clear the stored credentials via the SecretStore's clear method and re-authorize from scratch. The file-locked refresh mechanism ensures that only one process attempted the refresh, so you do not need to worry about race conditions causing the 401.

### How do I handle the case where a user has revoked access at the provider?

When a user revokes access to your application at the OAuth provider (for example, in Google's "Third-party apps with account access" settings), the stored refresh token becomes invalid. The next time the connection mixin attempts to use or refresh the token, it will receive a TokenRefreshError (typically with a 400 or 401 status code). The token lifecycle transitions to "expired-no-refresh." If auto_authorize is True, the mixin will automatically initiate a new authorization flow, asking the user to re-grant access. If auto_authorize is False, AuthorizationRequired is raised. Best practice is to catch both TokenRefreshError and AuthorizationRequired, clear the old credentials using `secret_store.clear(domain, provider, profile)`, and inform the user that their access was revoked and re-authorization is needed. The tombstone written by the clear operation ensures the system records that this was a revocation event, not simply a missing credential.

### What is the Provider User Context in error handling?

Provider User Context is additional contextual information attached to the AuthorizationRequired error that identifies which OAuth provider and which user profile triggered the error. It typically includes the provider name (such as "github" or "google"), the domain, and the profile name. This context is critical in applications that manage multiple OAuth connections simultaneously. When an AuthorizationRequired error is raised, the provider user context tells the application exactly which connection needs re-authorization, enabling it to present a targeted message like "Your Google connection for profile 'work' requires re-authorization" rather than a generic "Authorization required." The context flows from the connection mixin's configuration through to the error, ensuring no information is lost. Applications that manage multiple providers should use this context to route the re-authorization flow to the correct provider's authorize URL with the correct profile parameter.

## General Usage and Architecture

### What Python version and dependencies does mountainash-auth-client require?

Mountainash-auth-client requires intermediate-level Python features including Pydantic models (v2), Python Protocols (PEP 544, available since Python 3.8), and context managers. The core library depends on Pydantic for model definitions and validation, and uses standard library modules for file operations (os, tempfile), HTTP (urllib), and threading (for file locks). The OAuth 1.0a support has an **optional dependency** on the `authlib` library, which is not installed by default. If you attempt to use OAuth1Auth without authlib installed, the optional import guard raises a clear error message explaining the missing dependency. This design keeps the core package lightweight for the majority of users who only need OAuth 2.0. Other standard library dependencies include `hashlib` and `secrets` for PKCE code generation, `json` and `yaml` for serialization, and `http.server` for the LocalCallbackServer.

### How does the library handle concurrent access to credentials?

Concurrent access safety is built into several layers of the library. At the storage level, FilesystemStore uses atomic file writes (write to temp file, then rename) to prevent partial reads of credentials during concurrent write operations. At the refresh level, file-locked refresh ensures that only one process refreshes an expired token while others wait and then read the fresh credentials. At the model level, frozen Pydantic models prevent in-memory mutation of credentials, eliminating a class of concurrency bugs where one thread modifies a shared credential object while another is reading it. The lock method on SecretStore returns a context manager that provides exclusive access to a specific credential set (scoped by domain, provider, and profile). Custom SecretStore implementations should maintain these concurrency guarantees, particularly the lock mechanism, to ensure safe operation in multi-process environments.

### How is the library structured into modules?

The library is organized into approximately 10 modules reflecting its major concerns. The **auth types module** defines AuthSpec, all 13 concrete auth types, and the discriminated union type alias. The **OAuth flow module** contains OAuthFlow with PKCE, authorization URL building, token exchange, and refresh logic. The **OAuth 1.0a module** contains OAuth1Flow with the three-legged flow and authlib integration. The **connection mixins module** provides OAuth2ConnectionMixin and OAuth1ConnectionMixin with token lifecycle management. The **secret storage module** defines the SecretStore protocol and FilesystemStore implementation. The **callback server module** implements LocalCallbackServer and manual redirect fallback. The **dispatch module** contains the auth dispatch registry and kwargs conversion functions. The **error module** defines TokenExchangeError, TokenRefreshError, and AuthorizationRequired. This modular structure allows users to import only what they need and makes it straightforward to understand dependencies between components.

### Can I use this library with async/await?

The library's core design uses synchronous Python patterns (context managers, file I/O, HTTP requests). The OAuth flows, token refresh, and SecretStore operations are synchronous. However, the mixin-based architecture and Protocol-based interfaces mean that async wrappers can be built on top. You could implement an async SecretStore that wraps async file or network I/O, and create an async connection mixin that calls the OAuth flow in a thread executor. The LocalCallbackServer uses Python's `http.server` module, which is synchronous, but it only runs for the brief duration of an authorization callback and does not block the main event loop for long. For applications using asyncio, the recommended pattern is to run the authorization flow (which is interactive and infrequent) synchronously and use the resulting token for async API calls. Token refresh can be wrapped with `asyncio.to_thread` to avoid blocking the event loop.

### How do I configure the library for a new OAuth 2.0 provider?

To configure a new OAuth 2.0 provider, create an OAuth2AuthCodeAuth instance with the provider's specific endpoints and credentials. You need: the provider's **authorize URL** (where users are redirected to grant consent), the **token URL** (where authorization codes are exchanged for tokens), your **client ID** and **client secret** (obtained by registering an OAuth application with the provider), the **scopes** required for your use case, and a **redirect URI** (typically `http://localhost:PORT/callback`). Pass this auth spec to a connection class that uses OAuth2ConnectionMixin. On first `connect()`, the mixin will initiate the PKCE flow, open the browser, capture the callback, exchange the code for tokens, and store the credentials via SecretStore. Subsequent calls will load existing tokens and refresh them as needed. Each provider may have specific requirements for scopes, redirect URI formats, or token endpoint authentication methods, so consult the provider's OAuth documentation.

### What is the relationship between mountainash-auth-client and other mountainash packages?

Mountainash-auth-client is a focused authentication library within the broader mountainash ecosystem. It provides the auth type definitions, OAuth flows, and credential management that other mountainash packages consume. For example, mountainash-api-client uses the auth types and dispatch registry to authenticate API requests, while connection classes in other packages mix in OAuth2ConnectionMixin or OAuth1ConnectionMixin for automatic token management. The SecretStore protocol allows credential storage to be configured at the application level and shared across packages. The discriminated union of auth types serves as the common currency for authentication configuration across the ecosystem: any package that needs to describe "how to authenticate" uses an AuthSpec variant, and any package that needs to perform authentication uses the dispatch registry to convert that spec into driver-specific parameters.
